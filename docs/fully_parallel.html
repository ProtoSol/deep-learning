14.2 Fully Sharded Data Parallel

Large Scale Transformer model training with Tensor Parallel (TP)

Created Date: 2025-07-07

PyTorch FSDP2 provides a fully sharded data parallelism (FSDP) implementation targeting performant eager-mode while using per-parameter sharding for improved usability.

Umar Jamil's distributed training from first principles is the lecture for this chapter. This page is the sharded, fully parallel piece.

14.2.1 How FSDP2 works

In DistributedDataParallel (DDP) training, each rank owns a model replica and processes a batch of data, finally it uses all-reduce to sync gradients across ranks.

Comparing with DDP, FSDP reduces GPU memory footprint by sharding model parameters, gradients, and optimizer states. It makes it feasible to train models that cannot fit on a single GPU. As shown below in the picture:

  • Outside of forward and backward computation, parameters are fully sharded;

  • Before forward and backward, sharded parameters are all-gathered into unsharded parameters;

  • Inside backward, local unsharded gradients are reduce-scatterred into sharded gradients;

  • Optimizer updates sharded parameters with sharded gradients, resulting in sharded optimizer states.

FSDP can be considered a decomposition of DDP’s all-reduce into reduce-scatter and all-gather operations.

14.2.2 How to use FSDP2

The working sketch is fully_shared_dp.py, around the transformer in model.py. It is a ten-layer model with four heads, vocabulary 1024, and sequence length 64 — small enough to read, shaped like the model you would shard for real.

14.2.2.1 Model Initialization

Construct the module on every rank first, then shard it. The script loops over model.layers and calls fully_shard(layer), then fully_shard(model) so the root owns the leftover parameters (the embedding and the output head). After that the module is both a Transformer and an FSDPModule, which the two asserts check. Sharding a layer wraps its parameters as DTensors. Until fully_shard runs, each rank still holds a full replica, so the call belongs immediately after construction and before the optimizer is built.

14.2.2.2 Forward/Backward with Prefetching

A forward pass all-gathers the parameters of a layer just before that layer runs, computes as if they were local, and can free the unsharded copy afterward. Backward does the same for the gradient, then reduce-scatters it. FSDP2 overlaps the next layer's all-gather with the current layer's compute when prefetching is left on, which is the default: while layer \(i\) multiplies, layer \(i+1\) is already gathering. Explicit prefetch is the hook you set when the schedule should look further ahead than one layer, for example a backward prefetch recorded during forward. The script stops at construction; the next line you add is an ordinary loss.backward() on a batch of token ids. The communication is inside fully_shard, not in the training loop.

14.2.2.3 Enabling Mixed Precision

Pass a mixed-precision policy into fully_shard when the matmuls should run in bfloat16 or float16 while the master weights stay in float32. The reduction dtype for gradients can differ from the compute dtype. The model in model.py does not set a policy, so it trains in the parameter dtype. Turn the policy on only after the unsharded run fits and learns; a dtype bug looks like a divergence, and you want a float32 baseline to compare against.

14.2.2.4 Gradient Clipping and Optimizer with DTensor

After backward, gradients are sharded DTensors. clip_grad_norm_ on an FSDP2 root reduces the global norm across ranks and scales each shard, so you clip the root module rather than a local parameter list you assembled by hand. The optimizer — Adam is the usual choice — must be constructed after fully_shard, so its state (moments) is allocated per shard and not replicated. Clipping a full unsharded gradient that no rank holds is the mistake this ordering prevents.

14.2.2.5 State Dicts with DTensor APIs

model.state_dict() on an FSDP2 module returns DTensor values, one shard per rank. That is the right object to keep in memory for a same-world resume: load it back with load_state_dict on the same mesh and the shards line up. It is the wrong object to copy to a trainer that is not distributed. Summoning a full tensor on one rank gathers those shards; do it for a small module when you need to print a weight, not for a checkpoint of the whole model.

14.2.2.6 State Dict with DCP APIs

Distributed checkpoint (DCP) writes each rank's shard to its own file and records the metadata that can reassemble them on a different number of ranks. Call it with the FSDP2 state dict instead of torch.save on rank 0. Loading plans the shards onto whatever mesh you have now. Use DCP when the checkpoint has to outlive the job that wrote it. Use the raw DTensor state dict from the previous section when it does not.
